# SwarmCrate 产品方向与开发路线

确定日期：2026-10-27。本文由 AI 辅助制定，依据现有工程能力和公开工具/规范作产品判断，不把推断当作真实用户调研或采用量证明。实现保持 MoonBit 为主，围绕离线 BitTorrent 元数据与完整性核验推进。

| 优先级与方向 | 用户与实用价值 | 可持续扩展的交付物 | 完成标准 |
| --- | --- | --- | --- |
| P0：开源发布与数据集交付 | 发布维护者、数据集制作者在处理大目录前看清布局，再生成可复现的分发元数据 | 发布前规划、交付清单、种子/磁力链接与报告的组合导出、CI 发布示例 | 规划不读载荷；固定输入/参数的内容标识稳定；输出可被独立实现读取；不覆盖已有文件 |
| P1：离线镜像与资料库巡检 | 镜像维护者定位缺失、损坏与不可读范围，保存能对应到正确元数据的检查证据 | 带内容标识和范围的核验凭据、按文件汇总、待处理范围清单、批量巡检；有明确失效规则后再评估增量缓存 | 局部检查不能标成全量成功；报告能定位原始 infohash、文件与偏移；缓存不得仅凭时间戳冒充重新哈希通过 |
| P2：MoonBit 可复用完整性 SDK | 工具作者复用规划/核验/报告，而不依赖当前 Node CLI | 稳定的有类型 API、进度/取消语义、存储适配契约、可运行消费方与浏览器适配验证 | 根库保持 Wasm GC/JS；I/O 与核心分离；新接口兼容性有说明；取消、异常和资源上限可测试 |

三条方向共享同一核心与数据模型。近期先完成 P0 的一个完整链路，再推进 P1；P2 随公共 API 的实际需求逐步补强。暂不扩展下载器、做种、Tracker 服务或与上述目标无关的 UI。

## 为什么这样选

- [libtorrent 的创建文档](https://www.libtorrent.org/reference-Create_Torrents.html)把文件选择、属性设置、读取/哈希和编码分成不同阶段，指出读取所有载荷通常代价最高。这支持先提供无需载荷读取的发布前规划；它不证明某个用户群已经采用本项目。
- [BagIt（RFC 8493）](https://www.rfc-editor.org/rfc/rfc8493.html)体现了交付载荷、清单与校验信息之间的关系，可为后续交付凭据提供设计参考。当前 SwarmCrate 未实现 BagIt，不宣称兼容该格式。
- 当前项目已有真实文件创建、两套哈希、局部核验、错误定位及双后端 API，适合在同一离线流程上提高完整性和可集成性。先获得可复现的使用证据，再根据实际反馈决定更大范围扩展。

## 已落地与下一步

| 顺序 | 交付项 | 状态与验证方式 |
| --- | --- | --- |
| 1 | 发布前只读规划 `plan_torrent` / CLI `plan` | 已完成 0.7.0：真实字节、虚拟补零、两套分片计数、v1 哈希字节、v2 层字节上限；通过禁止打开载荷文件的真实测试，与实际种子独立解码结果对照 |
| 2 | 可保存的核验凭据与元数据身份绑定 | 本轮 0.8.0：`verify_with_receipt` / `--receipt` 绑定完整种子 SHA-256、infohash、真实文件映射、实际范围和结果；不可变快照，原 JSON/退出码兼容，普通未签名记录；27 个新增磁盘场景独立对照与保护验证 |
| 3 | 按文件的损坏/缺失/不可读汇总与待处理范围 | 下一项：在凭据之上实现；合并重叠范围，并明确详情被截断时不能给出完整修复清单，不自动修改用户载荷 |
| 4 | 公共 SDK 的进度与取消契约 | 在典型消费方验证后设计；需要证明取消不会留下冒充成功的报告或被误认为完整的输出 |

规划中的 `storage_bytes` 表示逻辑布局，不等于磁盘占用或网络流量；哈希层大小在去重前只是上限，完整 metainfo 的字节数/节点上限仍由实际创建校验。规划不生成内容哈希，也不是载荷核验。

## 每轮推进规则

先读本路线图、验收自查和发布流程，核对当前代码与未完成事项。一次完成一个可验证的用户链路，优先修复阻碍其使用的缺陷。真实开发、测试、文档、公开 CI、精确版本 Mooncakes 安装验证和版本标签形成闭环；不为了行数、测试数或提交数制造工作。
